# IPMS and System Flow Deep Dive

This document explains:
- why the IPMS module exists
- what each IPMS concept means
- where IPMS functions are called from
- the full runtime flow from boot to low-power entry and wakeup

Project root: `amara-flight-software2.0`

## 1) Why IPMS Exists

`IPMS` (Intelligent Power Management System) is the power-policy engine for the firmware.

Without IPMS, battery logic would be scattered across:
- ADC sampling code
- RTOS task loop code
- low-power HAL entry code
- wakeup ISR callbacks
- telemetry and logging

IPMS keeps the decision layer centralized:
- It decides the current power state from battery conditions.
- It decides whether low-power action is allowed by policy.
- It emits events for observability.

Execution of hardware transitions is intentionally separate:
- IPMS decides "what should happen".
- `System_Runtime.c` performs "how to enter/exit sleep/stop on this board".

This keeps the architecture modular and interview-defensible.

## 2) Key Files and Ownership

- `App/Inc/IPMS.h`
  - Public IPMS API, enums, config/status/event structs.
- `App/Src/IPMS.c`
  - IPMS state machine, thresholds, debounce, pending actions, event queue, wakeup bookkeeping.
- `Core/Src/freertos.c`
  - Calls IPMS in periodic `HealthPowerTask`.
- `App/Src/System_Runtime.c`
  - Executes low-power requests from IPMS and restores system after wake.
- `Core/Src/main.c`
  - Boot-time IPMS init + ISR callback handoff (`IPMS_OnRtcWakeup`, `IPMS_OnButtonWakeup`).
- `App/Src/Command_List.c`
  - CLI commands to query/override IPMS simulation and policy.

## 3) Core IPMS Vocabulary

### Power state
Current battery-health mode tracked by IPMS:
- `NORMAL`
- `LOW_POWER_WARNING`
- `SLEEP_CANDIDATE`
- `STOP_CANDIDATE`
- `RECOVERY`

### Policy mode
What actions IPMS is allowed to request:
- `MONITOR_ONLY`
- `ENABLE_SLEEP`
- `ENABLE_SLEEP_AND_STOP`

### Simulation mode
How battery input is sourced:
- `AUTO`: use measured battery voltage from ADC.
- `SUNLIGHT`: force effective voltage to configured sunlight value.
- `ECLIPSE`: force effective voltage to configured eclipse value.

### Pending action
One-shot request generated by IPMS:
- `ENTER_SLEEP`
- `ENTER_STOP`

The health/power runtime consumes this request and performs hardware entry.

## 5) Boot and Runtime Flow (End-to-End)

## 5.1 Boot initialization in `main.c`

`Core/Src/main.c`:
- `IPMS_GetDefaultConfig(ipms_config);`
- `IPMS_Init(ipms_config);`

This sets up:
- initial state (`NORMAL`)
- default policy (`MONITOR_ONLY`)
- default simulation (`AUTO`)
- event queue reset
- RTC wakeup IRQ enable

## 5.2 Scheduler starts

`main.c`:
- `osKernelInitialize()`
- `MX_FREERTOS_Init()`
- `osKernelStart()`

After this, the superloop no longer owns runtime logic.

## 5.3 HealthPowerTask periodic cycle

`Core/Src/freertos.c`, `RTOS_RunHealthPowerTaskCycle()`:
- refreshes watchdog if supervision allows
- calls `SystemRuntime_ReportIpmsEvents()` to drain IPMS events
- periodically reads ADC health data
- calls `IPMS_ProcessBatterySample(adc_sample.battery_voltage, now_ms)`
- polls `IPMS_GetPendingAction(&power_action)`
- if action exists, calls `SystemRuntime_ExecuteIpmsAction(...)`

So HealthPowerTask is the primary runtime owner of IPMS processing.

## 5.4 Decision algorithm inside `IPMS_ProcessBatterySample`

`App/Src/IPMS.c`:
- stores measured battery voltage
- computes effective battery voltage via simulation mode
- computes desired state from thresholds and current state (`IPMS_GetDesiredState`)
- applies sample-window debounce using `candidate_state` and `candidate_count`
- commits transition with `IPMS_ApplyState` when required sample count is met

`IPMS_ApplyState`:
- updates `power_state`
- updates counters (`transition_count`, sleep/stop entry counters)
- generates pending action if policy allows
- posts transition event to event queue

## 5.5 Pending action consumption and low-power execution

`freertos.c`:
- if `IPMS_GetPendingAction` returns true, call `SystemRuntime_ExecuteIpmsAction`

`App/Src/System_Runtime.c`, `SystemRuntime_ExecuteIpmsAction`:
- logs action type and duration
- calls `IPMS_ArmRtcWakeup(context->hrtc, duration_ms)`
- calls `SystemRuntime_PrepareForLowPower`:
  - stop ADC monitor
  - set radio to sleep
  - invalidate cached ADC sample
- refreshes watchdog and suspends tick
- enters sleep or stop:
  - `HAL_PWR_EnterSLEEPMode(...)` or `HAL_PWR_EnterSTOPMode(...)`
- restores system:
  - sleep: `SystemRuntime_RestoreAfterSleep`
  - stop: first `SystemRuntime_RestoreAfterStopMinimal` (clock + DMA + ADC only), sample/re-evaluate battery in short windows, and re-enter stop chunks while still not recovered
  - when IPMS reaches recovery criteria (no further low-power action and state converges), perform `SystemRuntime_RestoreAfterStop` full restore (UART/SPI/I2C/radio/etc.)
- disarms wakeup timer
- calls `IPMS_RecordWakeup(IPMS_WAKE_SOURCE_UNKNOWN, HAL_GetTick())`

## 5.6 Wakeup source handling

ISR callbacks in `Core/Src/main.c`:
- RTC wakeup IRQ callback calls `IPMS_OnRtcWakeup()`
- EXTI button callback calls `IPMS_OnButtonWakeup()`

These functions only set wake flags in IPMS.
Later, task context calls `IPMS_RecordWakeup` to:
- resolve wake source
- increment wake counters
- post wakeup event
- apply recovery transition

## 5.7 Event reporting path

IPMS posts events into its internal queue:
- state transition
- wakeup
- simulation mode change
- policy mode change

`SystemRuntime_ReportIpmsEvents()`:
- pops events with `IPMS_PopEvent`
- logs human-readable output
- sends telemetry events (`TELEM_EVENT_POWER_STATE`, `TELEM_EVENT_POWER_WAKEUP`, `TELEM_EVENT_POWER_MODE`)

This is how IPMS decisions become observable externally.

## 6) IPMS Public API and Where It Is Called

- `IPMS_GetDefaultConfig`
  - called from `main.c` during boot.
  - reason: seed deterministic baseline thresholds and timings.

- `IPMS_Init`
  - called from `main.c` during boot.
  - reason: initialize context, reset queue/flags, enable wake IRQ priority.

- `IPMS_ProcessBatterySample`
  - called from `freertos.c` in `HealthPowerTask`.
  - reason: evaluate battery and evolve state machine periodically.

- `IPMS_SetSimulationMode`
  - called from `freertos.c` health loop when draining queued control requests.
  - reason: apply operator-requested simulation mode in the single IPMS owner task.

- `IPMS_SetPolicyMode`
  - called from `freertos.c` health loop when draining queued control requests.
  - reason: apply operator-requested policy mode in the single IPMS owner task.

- `IPMS_GetStatus`
  - called from `Command_List.c` (`CMD_PWR_STATUS`).
  - reason: operator diagnostics snapshot.

- `IPMS_PopEvent`
  - called from `SystemRuntime_ReportIpmsEvents`.
  - reason: drain queued IPMS events for logs/telemetry.

- `IPMS_GetPendingAction`
  - called from `freertos.c` health loop.
  - reason: one-shot fetch of requested power action.

- `IPMS_ArmRtcWakeup`
  - called from `SystemRuntime_ExecuteIpmsAction`.
  - reason: ensure timed wake source exists before sleeping/stopping.

- `IPMS_DisarmRtcWakeup`
  - called from `SystemRuntime_ExecuteIpmsAction` after wake.
  - reason: prevent stale wake timer behavior.

- `IPMS_OnRtcWakeup`, `IPMS_OnButtonWakeup`
  - called from ISR callbacks in `main.c`.
  - reason: lightweight ISR notification only.

- `IPMS_RecordWakeup`
  - called from `SystemRuntime_ExecuteIpmsAction` after restore.
  - reason: classify wake source, count it, post wake event, force recovery state.

- `IPMS_*ToString` helpers
  - called from logging and command responses.
  - reason: readable status for operators and telemetry logs.

## 7) State-Transition Intent

High-level behavior:
- If battery drops, state moves toward warning then sleep candidate then stop candidate.
- If battery improves, state moves to recovery then back to normal.
- Entry and exit thresholds differ, giving hysteresis.
- Required consecutive samples prevent reacting to single-sample noise.

Action gating:
- State transition alone does not always trigger low-power entry.
- Policy mode determines whether sleep/stop actions are armed.

## 8) What to Watch While Debugging

Check these in logs:
- IPMS state transition logs from `SystemRuntime_ReportIpmsEvents`
- wakeup source logs (`RTC`, `BUTTON`, `UNKNOWN`)
- action logs in `SystemRuntime_ExecuteIpmsAction`
- telemetry power events queue results

CLI commands to use:
- power status command (`CMD_PWR_STATUS`)
- simulation command (`CMD_PWR_SIM AUTO|SUNLIGHT|ECLIPSE`)
- policy command (`CMD_PWR_POLICY MONITOR|SLEEP|FULL`)

## 9) Known Architectural Risks (Current Implementation)

- IPMS shared state and event queue are now guarded with short critical sections, but they are still not protected with an RTOS mutex.
- Command-side mode/policy updates are serialized through `Runtime_State` control requests and applied by `HealthPowerTask`.
- Wake flags are ISR-safe booleans; wake classification/clear now happens inside the same protected section as wake bookkeeping.

Recommended next hardening:
- consider a dedicated IPMS service queue (CMSIS queue + response flags) to provide explicit command completion acknowledgments
- optionally replace global interrupt masking with narrower RTOS-aware synchronization if latency budgets require it

## 10) Quick Mental Model

Use this sentence while reading code:

"IPMS decides policy state and action requests from battery + mode + policy; System Runtime executes hardware low-power transitions; HealthPowerTask drives the loop; ISR callbacks only annotate wakeup cause."
